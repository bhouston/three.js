# Gap 4 — glTF extension integration (EXT_neural_textures)

## Current state (code)

- `.ntc` is a **standalone, proprietary JSON manifest format** (`format: 'three-ntc'`, `version: 2`, checked in `NTCLoader.js`), loaded/saved only via `NTCLoader`/`NTCExporter`. Latent grids are base64-encoded uint8 inside the JSON; MLP weights are base64-encoded float16 inside the JSON. There is **no relationship to glTF whatsoever** in the runtime code: `grep`-ing `examples/jsm/ntc/`, `NTCLoader.js`, `NTCExporter.js`, `GLTFLoader.js`, and `GLTFExporter.js` for cross-references between "ntc" and "gltf" turns up nothing except unrelated MaterialX sample filenames and comment citations of glTF spec value ranges.
- A **draft, unimplemented** extension spec, `EXT_neural_textures.md`, already exists at the repo root, explicitly modeled on the NVIDIA paper. It defines: a root `extensions.EXT_neural_textures.neuralTextures[]` array (MLP arch descriptor + `weightsBufferView` pointing at real binary glTF bufferView data + a `latentGrid` descriptor referencing a normal glTF `textures[]` entry), and a per-material `extensions.EXT_neural_textures` block mapping output channel indices to `baseColor`/`normal`/`roughness`/`metallic`/`occlusion`/`emissive`.
- The team's own `.cursor/plans/ntc_consolidation.plan.md` flags this spec's disposition as an **open, unresolved question** — it hasn't been decided whether/how it fits into the current `examples/jsm/ntc/` consolidation.

## Why this matters

This is the most consequential gap relative to the user's stated goal ("particularly with regards to gltfs"): **there is currently no way to ship an NTC-compressed material inside a glTF file at all.** Every NTC asset today is a side-channel JSON file loaded independently of the scene graph, with no `extensionsUsed` declaration, no bufferView-based binary embedding (so latents/weights pay a ~33% base64 size+parse tax that real glTF `.glb` binary chunks avoid entirely), and no interoperability story for other engines/tools that might want to at least detect ("this glTF uses neural textures, fall back to X") even if they can't decode them.

## Proposed changes

1. **Decide and record scope**: is `EXT_neural_textures` meant to become a real, engine-agnostic ratified-style extension (implying careful compatibility with non-three.js consumers, a `KHR_`-style formal spec process, fallback textures for non-supporting viewers), or a three.js-specific pragmatic `EXT_` used only by three.js's own loader/exporter pair? This changes how conservative the format needs to be. Given the existing draft already targets external interoperability language ("Runtime engines (e.g., Three.js)..."), recommend treating it as the latter for v1 (three.js-only `EXT_`, documented as experimental) and revisiting formal ratification once real-world usage validates the field layout.
2. **Align the draft spec with the *actual* shipped format**, closing several concrete mismatches found during this comparison:
   - Draft's `arch.activation` is a single global string (`"relu"`) — real code supports (and gap 3 proposes extending) per-layer activation plus per-*output-channel* range activations (sigmoid/tanh/softplus) that the draft doesn't represent at all. The channel-mapping section (`channels: {baseColor, normal, roughness, metallic, occlusion, emissive}`) also needs extending to the repo's actual ~24-channel vocabulary (clearcoat, transmission, sheen, anisotropy, iridescence, etc. — see `NTCFormat.js`'s `CHANNELS`), or explicitly scoped down to a "core PBR subset" for v1 with a documented extensibility path.
   - Draft's `latentGrid` is a single flat descriptor (`baseResolution`, `levels`, `channelsPerLevel`) — doesn't yet reflect gap 1's proposed G0/G1 asymmetric pairing, or this repo's existing `mipsPerLevel` reuse-banding concept. Needs a real schema pass once gap 1 lands, not before (avoid ratifying a schema for an architecture that's about to change).
   - Draft stores weights via a real `weightsBufferView` (binary, FP16/FP32) — this is **better** than the current shipped format's base64-JSON weights and should be adopted back into the standalone `.ntc` path too, not just the glTF path (see item 4).
3. **Implement `GLTFExporter` plugin hook**: register an extension exporter (following the existing plugin pattern other extensions use, e.g. `GLTFMaterialsClearcoatExtension`) that, for any `NTCNodeMaterial` (or a material carrying a `cpuModel`/`activeChannels`), writes: (a) latent grid data into a real glTF `image`/`texture` (packed the same way `NTCHalfFloatTexture.js` already packs the mip chain — reuse that logic), (b) MLP weights into a binary `bufferView` (reuse `NTCBinaryCodec.js`'s float16 packing, just target a real ArrayBuffer/bufferView instead of base64 string), (c) the `EXT_neural_textures` JSON blocks (root + per-material).
4. **Implement `GLTFLoader` plugin hook**: register an extension parser that reads `EXT_neural_textures` back into the shape `NTCNodeMaterial` already expects (`{cpuModel, channelClassification}`), reusing `NTCLoader.js`'s `decodeLevel`/`decodeMLPLayersBase64`-equivalent logic but sourced from real bufferViews instead of base64 strings — this should let `NTCLoader.parse()` and the new glTF parser share a common "manifest → cpuModel" core function rather than duplicating decode logic.
5. **Binary bufferView storage for the standalone `.ntc` format too**: once the bufferView-based codec exists for glTF, consider whether `.ntc` itself should move to a binary container (e.g. a small custom `.glb`-like binary framing, or literally becoming a single-node glTF file using the same extension) rather than base64-in-JSON — this alone recovers the ~33% base64 overhead on every shipped `.ntc` sample (current samples are ~93KB each; meaningful savings at scale).
6. **Round-trip test**: extend `test/vitest/*/ntc/` with a glTF-specific round-trip test (export a trained `NTCNodeMaterial` into a `.glb`, reload via `GLTFLoader`, assert `cpuModel`/`activeChannels` and rendered output match the pre-export material) mirroring the existing `NTCManifest.test.js`/`NTCLoader`+`NTCExporter` coverage pattern.

## Suggested sequencing

1. Scope decision (item 1) — blocking, cheap, should happen before any code.
2. Binary bufferView packing for weights+grids as a shared utility (item 3/4's shared "codec" piece, item 5's motivation) — this is valuable independent of glTF (shrinks standalone `.ntc` files too), so it can land and be tested first without touching `GLTFLoader`/`GLTFExporter` at all.
3. `GLTFExporter` write path.
4. `GLTFLoader` read path + round-trip test.
5. Revisit/update `EXT_neural_textures.md` to match whatever schema actually shipped, including a version/`experimental: true`-style marker until the format stabilizes across gap 1/2/3 changes.

## Risks

- Coupling the glTF schema to the current architecture before gaps 1–3 land risks ratifying a format that immediately needs a breaking v2 — recommend explicitly marking the extension `EXT3_neural_textures` or similar "experimental/unstable" in its own doc until the underlying model architecture (grids, quantization, activations) settles.
- glTF ecosystem tooling (validators, other engines, asset pipelines) will not recognize `EXT_neural_textures` and will either ignore the material entirely (falling back to `pbrMetallicRoughness` base values, which is the *correct* graceful-degradation behavior per glTF's extension model, and should be explicitly tested) or, if authored without fallback values, render an untextured/default-gray material — the exporter should always populate reasonable `pbrMetallicRoughness`/texture fallback fields alongside the extension block.
- Binary bufferView packing changes shift where GPU-upload-ready data comes from (parsed glTF buffer vs. a JS `Float32Array` in a JSON manifest) — needs care to avoid extra copies on load for large latent grids on memory-constrained mobile devices.
