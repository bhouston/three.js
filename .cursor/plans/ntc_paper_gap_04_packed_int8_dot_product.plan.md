# Gap 4 (follow-up) — WebGPU `packed_4x8_integer_dot_product` for the MLP decoder

## Origin

Not one of the original five paper-comparison gaps — a follow-up investigation requested mid-session: "look into adding a run-time option of using the WebGPU-only `packed_4x8_integer_dot_product` language extension... it may require quantization during training of the MLP in addition to the already existing quantization of the latent feature grids... if feasible add it as an option so we can compare effectiveness." This doc records the investigation and what was actually implemented, in the same spirit as the other gap plans.

## What it is

[`packed_4x8_integer_dot_product`](https://developer.mozilla.org/en-US/docs/Web/API/WGSLLanguageFeatures) is a WGSL capability providing `dot4I8Packed(u32, u32) -> i32` / `dot4U8Packed(u32, u32) -> u32`: a 4-wide signed/unsigned int8 dot product (4 multiply-adds, accumulated as one integer) from two `u32`-packed operands, in a single call — potentially mapping a hidden layer's `dot(weightsRow, inputVector)` onto one native integer instruction instead of 4 scalar fp32 multiply-adds.

## Two real surprises during investigation (both confirmed empirically, not just read off a spec)

1. **It's a WGSL *language feature*, not a device *feature*.** Checked via `navigator.gpu.wgslLanguageFeatures.has(...)`, available before ever requesting an adapter/device — distinct from `renderer.hasFeature(...)`/`device.features` (e.g. `shader-f16`, already used by `NTCMLPTSL.js`'s `supportsHalfPrecisionStorage`). Confirmed present in this session's own test Chromium (macOS, Metal/ANGLE backend).
2. **It needs no `enable` directive at all** — this was the opposite of the first (reasonable, spec-informed) assumption. A WGSL *extension* (`f16`, `subgroups`, etc.) requires `enable <name>;` as the first statement in the shader module, and three.js's `WGSLNodeBuilder.enableDirective(name, stage)` — the only mechanism that places one there correctly — isn't part of the public `three`/`three/tsl` API surface (no plain `Node` base class for addon code to subclass with its own `generate(builder)`; `NodeMaterial.prototype.setup(builder)` was identified as the one place addon code *does* get a live builder reference). An initial implementation emitting `enable packed_4x8_integer_dot_product;` via exactly that route was rejected outright by Chromium's WGSL compiler ("expected extension", listing only `f16`/`subgroups`/etc. as valid names) — removing the directive entirely fixed it. `dot4I8Packed`/`dot4U8Packed` are directly callable the moment `supportsPackedDotProduct(renderer)` returns true, with **no special material-level wiring required**.

## What was implemented

- **`NTCPackedDotProduct.js`** — `supportsPackedDotProduct(renderer)` capability check; `dot4I8PackedTSL`/`dot4U8PackedTSL` (raw WGSL wrappers via `wgslFn`); CPU-side `packInt8x4`/`quantizeSymmetricInt8`/`computeSymmetricScale` (symmetric, per-tensor int8 quantization primitives).
- **`NTCMLPQuantization.js`** — post-training (not quantization-aware-trained) int8 quantization of the decoder's *hidden* layers only. Activation quantization ranges are derived **analytically** (closed-form interval/worst-case bound propagation through each layer's actual trained weights: `computeDecoderInputBound` scans the real latent grids for their current max-abs value; `computeLayerPreActivationBound` applies the triangle inequality per output neuron; `computeActivationOutputBound` propagates that bound through relu/hgelu, including hardGELU's own non-monotonic minimum at x=-0.75), not by calibration-sampling real inputs. This trades some wasted quantization resolution for a hard correctness guarantee: nothing can silently saturate on data the calibration set didn't happen to cover.
- **`NTCMLPTSL.js`** additions — `quantizeAndPackInt8TSL` (live, per-invocation GPU-side quantize+pack of activations) and `evaluateHiddenLayerDot4I8` (the actual dot4I8Packed-based hidden-layer evaluator, dequantizing via one `result * weightScale * inputScale` multiply, bias always fp32).
- **`NTCDecoderTSL.js`** — `evaluateNeuralTextureRaw` gained `options.useInt8DotProduct` (default `false`): when true and supported, every *hidden* layer runs through `evaluateHiddenLayerDot4I8`; the final (always-linear) output layer is deliberately **never** quantized this way (narrow — a handful of physical PBR channels — and feeds shading directly, where int8's coarser precision would be most visible). Silently falls back to the existing fp32/fp16 mat4 path whenever unsupported, so callers can request it unconditionally.
- **`NTCNodeMaterial.js`** — `options.useInt8DotProduct` threaded through to the constructor's `evaluateNeuralTextureRaw` call. No `setup()` override needed (see surprise #2 above).
- Wired into `webgpu_materials_neural_texture_compression.html` (viewer) as a GUI checkbox that rebuilds all 7 loaded sample materials with the option toggled, for direct visual/before-after comparison.

## Numerical limitations — answering the original question directly

Yes, real and worth documenting plainly:

- **Weights**: quantized once, post-training, to a single symmetric per-tensor int8 scale per hidden layer (not per-channel, not QAT). This is the same category of scheme `NTCQuantization.js` already applies to latent grids, just simpler (no asymmetric/zero-preserving option — weights are already roughly zero-centered from He init, so the asymmetric correction that matters for latents at very low bit depths isn't as necessary here).
- **Activations**: quantized *dynamically*, per-shader-invocation, using a *statically computed* (analytical, not calibrated) scale. Because the scale is a conservative worst-case bound rather than a measured typical range, real activations under-utilize the available int8 levels somewhat.
- **Compounding across layers**: measured directly (see `test/vitest/browser/ntc/NTCPackedDotProduct.test.js`'s full-decoder test) on a small 2-hidden-layer (8×8), artificially weight-scaled network: mean absolute error ≈0.025, max ≈0.16 against the fp32 reference — a real, non-trivial degradation, but far short of visually catastrophic for typical rendering use, and measured *without* any quantization-aware training at all.
- **The user's own hypothesis was correct**: proper quantization-aware training of the decoder's weights *and* activations (not just latents, as `NTCQuantization.js` already does) would very likely close most of this gap, the same way `NTCQuantization.js`'s QAT (Section 4.2-style STE) does for the latent grids today. That's the natural next increment if this path proves worth pursuing further — not attempted in this pass, scoped out deliberately to keep this addition comparable in size/rigor to the other three stages landed the same session (a genuine, tested, working "compare effectiveness" baseline, not a half-finished QAT rewrite).

## A real bug this surfaced during development (fixed, with a regression test)

The very first attempt at an end-to-end (real trained-shaped weights, multi-layer, real texture sampling) correctness test showed drastic, "wrong axis"-looking error (mean ≈1.8, max ≈8.4 — nowhere near the ≈0.025/0.16 eventually confirmed correct). Root cause, found by successive isolation (hand-picked single-neuron cases → chained layers with hand-picked values → chained layers via the real `buildInt8HiddenLayers` output fed constants → full pipeline via real texture sampling): the test's own `baseResolution: 8` render target/grid was **narrower than 32 texels**, hitting the *pre-existing, already-documented-elsewhere-in-this-test-suite* WebGPU RGBA16F readback row-alignment bug (silently zeroing most texels, not just losing precision) — not a bug in the int8 implementation at all. Fixed by using `baseResolution: 32`; the test's own comments now document this explicitly so a future reader doesn't have to re-derive it.

## Suggested follow-ups (not done here)

1. **Benchmark actual speedup** on real mobile/desktop hardware — this pass focused entirely on correctness/feasibility; no perf numbers were collected. Without a measured win, this remains a "can compare, hasn't been shown to help" feature.
2. **Quantization-aware training** of hidden-layer weights/activations (the natural next increment - see "Numerical limitations" above) if benchmarking shows the fp32→int8 speedup is worth the accuracy cost's current size.
3. **Per-channel weight scales** (rather than per-tensor) - a common accuracy improvement in int8 ML quantization generally, at the cost of a per-output-neuron scale factor instead of one scalar per layer (still compatible with `dot4I8Packed`'s per-call dequantization, just needs an extra `getWeightScale(outputIndex)` closure).
4. **Extend to the final output layer** once accuracy at the hidden layers is validated as acceptable in practice - deliberately excluded from this first pass.
