# Gap 5 — Mobile precision fallback, decode budget, and multi-material scaling

## Current state (code)

- **fp16 GPU storage is conditional and likely unavailable on many mobile devices today.** `NTCMLPTSL.js`'s `supportsHalfPrecisionStorage()` requires `renderer.backend.isWebGPUBackend === true` **and** `renderer.hasFeature('shader-f16') === true`. When either is false (WebGL2 always; WebGPU without the `shader-f16` optional feature, which is common on current Android WebGPU/ANGLE-Vulkan and mobile Safari/Metal implementations), MLP weights fall back to fp32 `uniformArray` — doubling weight-buffer bytes and giving up the throughput benefit the whole `mat4`-packing design assumes. This fallback is silent (no warning, no size-impact surfaced to the developer) and there's no code path measuring or reporting which mode a given deployment actually landed in.
- **Latent grids are deliberately kept at RGBA16F** (not RGBA32F) specifically because "RGBA32F isn't filterable under WebGPU without an opt-in feature" (`NTCHalfFloatTexture.js`) — a good mobile-aware decision already in place, worth preserving through any gap-1/gap-2 changes.
- **No compute shaders at inference** — good; the decode path is a single `textureLevel` fetch + MLP eval per pixel, control-flow-branch-free with respect to LOD selection, which is the right shape for tile-based mobile renderers.
- **No SIMD-divergence handling exists** (the paper's Appendix A concern — many different materials' MLPs active within one SIMD/warp group during ray tracing). This doesn't directly apply to three.js's raster decode path today, but the *analogous* mobile-relevant cost is real: **each `NTCNodeMaterial` is a fully separate material instance** with its own baked-in weight/latent uniforms, so a glTF scene with N distinct NTC materials means N distinct shader programs/pipelines and (per normal three.js behavior) N draw calls — nothing in this codebase batches or atlases multiple trained NTC materials into a shared dispatch. For a typical glTF asset with dozens of unique materials, this is a real CPU-side and pipeline-switch cost on mobile that the paper's GPU-ray-tracing-specific Appendix A doesn't even address (it assumes far fewer, larger draws).
- `.toVar()` materialization in `NTCMLPTSL.js` is called out in comments as a **required correctness workaround** for a WGSL private-address-space/parser-recursion limit, not an optional optimization — worth flagging since any gap-2/gap-3 changes that widen the MLP (more inputs, more hidden units) risk re-triggering this limit and need the same treatment applied consistently.

## Why this matters for mobile + glTF

A glTF asset optimized in isolation (single material, desktop browser, WebGPU + `shader-f16`) can look great in the example pages and still ship a 2× larger-than-expected weight buffer and janky frame pacing once loaded into a real mobile scene with many materials. This is the category of gap that won't show up in per-material PSNR/size benchmarks (gaps 1–3) or in a glTF-conformance check (gap 4) — it only shows up under realistic multi-material, real-device load, which is exactly the scenario the user is asking about ("mobile usage... particularly with regards to glTFs").

## Proposed changes

1. **Surface precision-fallback state explicitly**: add a diagnostic (e.g. `NTCNodeMaterial.precisionMode` getter, or a console warning gated behind a dev flag) reporting whether a given material landed on the fp16-storage-buffer path or the fp32-uniform fallback, and what that means for its actual VRAM footprint (extend `NTCModelSize.js`'s `computeModelFootprint` to take the *actual* detected renderer capability rather than always assuming the optimistic fp16 path, or always assuming the pessimistic fp32 path as it seems to today per the trainer agent's findings).
2. **Add a "conservative mobile" precision profile** that never depends on `shader-f16` — i.e., a preset (paired with plan 03's `NTC_PROFILES`) that's sized assuming fp32 weights from the start, so its advertised size/quality numbers are honest on the broadest device set rather than only achievable on the subset of devices with `shader-f16`.
3. **Investigate low-cost multi-material batching**: since NTC materials are, by construction, small (weights are a few KB, latents are the bulk of the size), investigate whether multiple trained NTC materials for one glTF asset could share a single shader program with weights/latents indexed by a per-instance/per-primitive uniform or storage-buffer offset (analogous in spirit to the paper's Appendix A "iterate over unique parameter offsets, broadcast across the SIMD group" trick, but applied to draw-call reduction rather than warp divergence). This is exploratory — even a partial win (e.g. batching materials that share identical `arch`/channel layout, differing only in weight/latent values) would meaningfully help typical glTF scenes with many material variants of the same template (e.g. procedurally-varied materials).
4. **Budget and document decode ALU/bandwidth cost per profile**: extend the `NTC_PROFILES` table (plan 03) with a measured (not just theoretical) ms/pixel or ms/frame figure per profile on at least one representative mid-tier Android and one Apple mobile device, analogous to the paper's Table 4 (`0.49ms` BC-high vs `1.15–1.92ms` NTC at 4K) — this is the number a glTF asset author actually needs to decide whether NTC is worth it for a given target device tier.
5. **Re-validate the `.toVar()` workaround's threshold** whenever gap 2/gap 3 changes widen the MLP input/hidden dimensions — add a regression test that trains/evaluates the largest planned preset (`desktop-quality`, 2×64 + wider input from positional encoding) end-to-end on WebGPU to catch a WGSL compile failure before it ships.

## Suggested sequencing

1. Diagnostics for precision-fallback state (cheap, standalone, immediately useful for debugging "why is this material bigger than expected on my phone").
2. Conservative mobile profile sizing (pairs naturally with plan 03's preset work — do together).
3. On-device ms/frame measurement harness (shared with plan 02's profiling need — build once, reuse for both).
4. Multi-material batching investigation — treat as a research spike with a go/no-go decision point, not a committed deliverable, since it's the least-understood item here and may require deeper renderer/material-system changes than the rest of this comparison.

## Risks

- `shader-f16` adoption on mobile WebGPU is outside this project's control and may simply take time (browser/driver updates) — the "conservative mobile" profile is a hedge, not a fix, and should be clearly labeled as trading some VRAM efficiency for broad compatibility.
- Multi-material batching, if pursued, is a bigger architectural change than anything else in this comparison (touches material system, not just the NTC addon) and could be deprioritized entirely if draw-call counts in practice turn out not to be the bottleneck for typical NTC-using glTF scenes — validate with real profiling before investing here.
