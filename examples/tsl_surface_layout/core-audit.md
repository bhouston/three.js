# Core audit: composable surface outputs and temporal resources

Pinned fork: `bhouston/three.js`, dev `d7848108d3c2b93c322b99fe41b4c3dbafa620b5`. This audit reads the fork at that revision; statements below do not imply these implementations are upstream. CPU probes ran directly against this source. No renderer/GPU result is claimed by this document.

## Recommendation

Start with A plus a thin B convention: a function creates a configured PassNode, declares only the physical attachments used by its preset, and returns stable ordinary sampleable nodes with metadata/codec descriptors. Use the existing `sample( uv => decode( backing.sample( uv ) ) )` primitive for semantic views. Keep the physical depth TextureNode available separately. Build later resources as separate named values (`reflectionRaw`, `reflectionFiltered`, `opaquePrevious`), rather than overwriting a shared `reflection` property. Rebuild the owned graph on structural changes. A class is optional; a plain frozen return object is enough.

Do not make a surface container responsible for transient aliasing, broad resource versioning, histories or dependency validation. C is useful only when application scale justifies a setup-time immutable-handle binding/validation phase. D would require substantial new resource declarations and scheduling machinery; RenderPipeline is currently a root output node rendered through a fullscreen material, not a resource graph compiler.

## Exact producer dependency chain

1. [`PassTextureNode.setup`, PassNode.js L66-L71](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L66-L71) assigns `builder.getNodeProperties( this ).passNode = this.passNode`. Merely returning a raw Texture does not do this.
2. [`Node.build`, Node.js L1164-L1208](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/Node.js#L1164-L1208) marks setup initialized, invokes setup, recursively builds every Node-valued entry of its builder properties, then calls `addSequentialNode(this)`. This is postorder traversal of the reached shader node graph. A decoded expression retains the producer when its expression actually reaches the PassTextureNode.
3. [`NodeBuilder.addSequentialNode/buildUpdateNodes`, L859-L919](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/NodeBuilder.js#L859-L919) appends FRAME/RENDER before/after nodes to a Set after child processing, then builds ordered update arrays.
4. [`NodeManager.updateBefore`, L1077-L1089](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/renderers/common/nodes/NodeManager.js#L1077-L1089) walks the material's updateBeforeNodes, using the current render object's NodeFrame. [`Renderer`, L4114-L4143](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/renderers/common/Renderer.js#L4114-L4143) invokes these before bindings/pipeline/draw.
5. [`NodeFrame.updateBeforeNode`, L155-L198](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/NodeFrame.js#L155-L198) deduplicates by `node.updateReference(frame)` and frameId/renderId, and marks the frame BEFORE invoking `updateBefore`. [`PassNode`, L494-L508](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L494-L508) defaults to FRAME. Multiple reached views of the same PassNode therefore do not inherently render that pass multiple times per frame. Multiple cameras should use separate pass instances; mutating one PassNode's camera twice within a frame does not create independent scheduling identities.

This is real useful dependency plumbing, with limits: dependencies inside a geometry material/context may only become known when that material compiles during a nested render; a pass's private `_mrt` is not eagerly traversed by PassNode.setup. A dependency needed only as a depth attachment is absent from the sampling graph. A raw `getTexture()` followed by `texture(raw)` loses the producer, as does attaching the raw texture to another render target. Graph traversal does not inspect shared Texture identity to derive read/write hazards. There is no general cycle diagnostic, barrier planner, attachment alias analysis or resource liveness allocator here.

An existing explicit ordering hook is [`Node.before(node)`, L1078-L1086](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/Node.js#L1078-L1086). [`Node.build`, L1110-L1126](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/Node.js#L1110-L1126) builds these nodes before the receiver, so an attachment-only consumer can explicitly put the depth producer before it. This is an ordering expression, not resource hazard validation. Its use needs an execution probe for the chosen composition.

## Allocation and layout freeze

[`PassNode.getTexture`, L626-L651](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L626-L651) clones the first color texture when a named texture is first requested, adds it to `_textures`, and pushes it to `renderTarget.textures`. [`getTextureNode`, L710-L724](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L710-L724) calls updateTexture immediately, so requesting the node eagerly creates that CPU attachment even if it is never ultimately reached by final output. GPU allocation happens when used by the renderer. Repeated requests return the cached node/texture.

[`MRTNode.setup`, L251-L278](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/MRTNode.js#L251-L278) looks up each output name in the actual target textures and ignores absent names. This is declaration-versus-allocation separation, not arbitrary demand pruning. A previously requested attachment remains in the target if an effect disappears. There is no PassNode removal API; changing MRT declarations or final output does not reclaim that attachment. Reconstructing a pass is the safe supported pattern for removal/repacking. The local CPU probe proves setMRT(null) retains the attachment count.

[`MRTNode.merge`, L234-L248](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/MRTNode.js#L234-L248) creates a new MRTNode; later output, blend and clear dictionaries overwrite duplicate keys. [`OutputStructNode.generate`, L71-L113](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/OutputStructNode.js#L71-L113) caches the member layout in builder node data and generates every indexed member. Do not allocate a physical attachment without a matching populated output member: sparse MRT members are not a declared supported layout.

If roughness activates `normalRough`, its writer must write the entire defined packed vec4, including the normal channels. MRTNode prunes at attachment granularity; it does not prove which channels consumers need or synthesize partial writes. A demand-aware B descriptor could delay `getTextureNode(storage)` until a field is requested, but once requested the attachment persists until reconstruction. Compile the descriptor once after collecting the preset's uses; reject structural mutation after freeze. Adding a consumer that needs a new physical attachment requires rebuild/recompile; adding another consumer of an existing field can reuse the field node with the normal pipeline needsUpdate/rebuild rules.

[`PassNode.compileAsync`, L796-L823](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L796-L823) explicitly documents configuration must finish first. `setMRT()` itself just assigns `_mrt`; there is no ownership-level layout generation or invalidation transaction. [`PassNode.setup`, L826-L839](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L826-L839) sets samples from options/renderer, overwrites the DEFAULT color texture type with `renderer.getOutputBufferType()`, and selects FloatType depth for reversed depth. Configure and verify physical formats on the actual target; do not assume the constructor's `type` wins for the first output. Additional color attachments inherit clone-time properties. [`NodeBuilder.getOutputType`, L660-L672](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/core/NodeBuilder.js#L660-L672) derives shader output component type from the actual target texture.

The fork's RenderTarget supports count:0 (depth-only), but PassNode's constructor unconditionally uses `renderTarget.texture.name` at L254. Passing count:0 to depthPass throws in the CPU probe. The helper called depthPass selects a depth result; it does not itself establish colorless rendering. Do not conflate that API name with a true depth-only target/pass optimization.

## Sampleable semantic views

The existing [`SampleNode`, L67-L81,L99](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/utils/SampleNode.js#L67-L99) is precisely useful for a codec view:

```js
const storage = scenePass.getTextureNode( 'normalRough' );
const surface = Object.freeze( {
  depth: scenePass.getTextureNode( 'depth' ),
  normal: sample( uv => octDecode( storage.sample( uv ).rg ) ),
  roughness: sample( uv => storage.sample( uv ).b ), // perceptual contract
  camera
} );
const aoRaw = ao( surface.depth, surface.normal, camera );
// Store raw/temporal/spatial as separate constants/immutable handles.
```

Each returned decode expression still reaches storage's producing pass. There is no need to turn decoded normal data into a new full-screen render target. [`convertToTexture`, RTTNode.js L384-L390](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/utils/RTTNode.js#L384-L390) returns SampleNode unchanged; ordinary arithmetic without a sampleable wrapper may become RTT when converted.

Effect contracts are broader than Node<vec3>, but not uniformly generic: [`GTAONode`, L413-L429](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/examples/jsm/tsl/display/GTAONode.js#L413-L429) calls depth.sample, depth.gather and normal.sample, and the no-normal fallback reads depth.value. [`SSGINode`, L426-L440](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/examples/jsm/tsl/display/SSGINode.js#L426-L440) similarly samples semantic normals and uses physical depth. SSR samples normal at secondary UVs (L1135) and uses it as a normal expression (L895); SampleNode satisfies both. TRAA needs physical depth.value and beauty's renderTarget (see below). Keep metadata alongside ordinary nodes, rather than forcing effects to import a container type.

Packed normals generally need nearest sampling followed by decode and normalize. Interpolating encoded octahedral values across folds is not equivalent to interpolating decoded unit normals; a codec's filtering contract must say nearest or decode-aware filtering. ColorSpace, normal coordinate space and roughness convention belong to the view contract, while format/sampler/channels belong to storage. Integer IDs need integer attachments or explicitly normalized encodings plus nearest sampling. Avoid invalid three-component float targets: for oct normal plus roughness use a renderable four-component target (e.g. RGBA16F) or separate RG16F+R8 where supported. Do not infer byte limits from channel sums: validate against actual WebGPU device limits and format alignment. The core does not provide a semantic packing solver.

## History and hazards

[`getPreviousTexture`, L663-L675](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L663-L675) clones the current texture on first call. [`toggleTexture`, L684-L705](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L684-L705) exchanges color texture references in the target and updates current+previous cached nodes. [`updateBefore`, L889-L895](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L889-L895) swaps ALL registered histories before rendering this frame. `getPreviousTextureNode` creates the current node first (L739-L746), ensuring both cached nodes exist for toggle. Raw getPreviousTexture alone does not provide these cached nodes, yet toggle assumes them; use the node API rather than mixing these paths.

PreviousTextureNode is still a PassTextureNode, so its setup exposes the SAME producer edge. It is not a special temporal edge that means "read last frame without executing the producer." Merely requesting previous data can schedule the producer and its swap. It does not independently validate a current-frame cycle. Initialized-node guards/frame dedup prevent some recursion, but do not constitute a feedback-hazard rejection mechanism. Explicitly stage feedback with private history buffers/copies and a clear frame lifecycle.

**Confirmed previous-depth defect in this revision:** depth is stored in renderTarget.depthTexture and `_textures.depth`, not `renderTarget.textures`. toggleTexture('depth') looks up index -1 and writes an array property `textures['-1']`; it swaps node references while leaving the actual depth attachment unchanged. CPU probe verifies this. Therefore `getPreviousTextureNode('depth')` must not be described as supported color-equivalent ping-pong history. TRAA owns a separate depth history and copies current depth instead.

PassNode lacks first-frame history seeding, camera-cut/history-invalidation API and automatic format-change history reconstruction. Previous textures clone once, so late storage format changes do not propagate to already-created history clones. [`Texture.copy`, L495-L499](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/textures/Texture.js#L495-L499) shares the source object for color texture clones; [`DepthTexture.copy`, L81-L85](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/textures/DepthTexture.js#L81-L85) makes a new source. CPU image dimensions alone do not prove both history GPU resources resized correctly. Rebuild histories on layout/quality/resolution changes and test GPU allocations, rather than inferring full lifecycle guarantees from getPreviousTextureNode.

## Depth ownership, reuse and execution

[`PassNode` constructor L258-L285](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L258-L285) accepts an externally supplied depthTexture. The producer owns the depth texture if its renderTarget is the first owner. [`RenderTarget.depthTexture` setter L335-L340](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/core/RenderTarget.js#L335-L340) assigns renderTarget ownership only if null; external users do not steal it. [`Textures.updateRenderTarget`, L165-L172](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/renderers/common/Textures.js#L165-L172) resizes depth only through the owner, and [`_destroyRenderTarget`, L624-L660](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/renderers/common/Textures.js#L624-L660) destroys depth only through its owner. Dispose consumers before the producer, and do not retain a consumer after its imported depth owner is disposed.

Pass autoClearDepth defaults true (L338); attachment reuse needs autoClearDepth:false (or equivalent all-clear policy), explicit producer order, compatible dimensions/layers/sample counts and storeMultisampledDepthBuffer preservation. [`WebGPUBackend`, L950,L1030-L1047](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/renderers/webgpu/WebGPUBackend.js#L1030-L1047) maps no-clear to depth load, but multisampled depth discard explicitly forces clear/discard. [`Material.depthFunc`, L211](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/materials/Material.js#L211) defaults LessEqualDepth; [`WebGPUPipelineUtils`, L953-L1004](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/renderers/webgpu/utils/WebGPUPipelineUtils.js#L953-L1004) reverses comparisons when reversedDepthBuffer is enabled. PassNode does not set a special equal depth comparison for prepass shading.

A depth overdraw optimization needs identical vertex/deformation/displacement/jitter/projection/alpha coverage between depth and shade passes, consistent sample count and precision, appropriate depth comparison (often equal/no depth writes, or carefully chosen less-equal), and enough fragment work saved to pay for extra geometry. Coplanar surfaces/alpha test/custom depth can invalidate equivalence. Sharing a texture without testing these conditions is not evidence of a useful depth prepass.

Device-depth metadata must include projection and reversed-depth conventions. [`PassNode.getViewZNode`, L763-L767](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/PassNode.js#L763-L767) always uses perspectiveDepthToViewZ; getLinearDepthNode includes a camera-type TODO at L790. [`ViewportDepthNode`, L183-L195,L233-L245](https://github.com/bhouston/three.js/blob/d7848108d3c2b93c322b99fe41b4c3dbafa620b5/src/nodes/display/ViewportDepthNode.js#L233-L245) handles reversed-depth formula branches, but that does not make the PassNode helper automatically orthographic-correct. Semantic depth access should use the right camera-aware conversion/inverse projection, rather than silently treating all raw depth as linear depth.

## Existing versus addon versus core work

| Concern | Existing facility | Small addon/convention | Requires larger/core work |
|---|---|---|---|
| Per-pass named attachments | PassNode.getTextureNode, MRTNode | Freeze a preset layout; create only needed storage nodes | Automatic retained-attachment removal/repacking |
| Semantic decode at arbitrary UV | SampleNode callback; ordinary TSL | Metadata + encode/decode descriptors | No core change needed for B |
| Shared channels | One vec4 MRT writer, multiple views | Validate field overlaps/types/filtering, write all channels | General packing solver if desired |
| Current pass dependencies | PassTextureNode + setup/postorder + FRAME dedup | Explicit before for attachment-only use; stable function return values | Resource access/hazard validation and cycle diagnostics |
| Produced after surface | GTAO/SSGI/SSR/RTT passTexture outputs | Distinct immutable values/handles per stage | No universal GBuffer needed |
| Declare then bind later | Custom Node.setup can return a bound node | Seal/bind-once phase; unresolved/cycle errors; versioned handles | Dynamic rebinding after compilation needs reliable recompilation/cache invalidation machinery |
| History | PassNode color ping-pong; effects own histories | Explicit previous-frame imports, invalidation/seeding; dispose list | Generic correct previous-depth support, broad temporal-edge/resource version model |
| Depth attachment reuse | External depthTexture + no clear + material depth state | Explicit producer ordering/compatibility validation | Resource graph deriving attachment dependencies automatically |
| Resource lifetime | Per-target disposal and effect methods | Explicit ownership; graph replacement | Transient liveness allocation/aliasing; barriers; pooling |
| Material integration | MRT, material MRT, context, overrideNodes | Document AO/GI/radiance conventions | No forced renderer architecture needed |
| Low presets | Omit consumers/attachments before construction | Rebuild on structural toggles; preserve uniforms where valid | Automatic target pruning not currently present |

## A/B/C/D assessment and testable boundaries

A removes repetition through a function returning ordinary sampleable fields, explicit context injection, effect ownership and one rebuild path. This already addresses the common example integration problem. B earns its existence if multiple examples need interchangeable physical packing while keeping the same effect call sites; it can remain a small descriptor plus factory instead of a mandatory class. Separate per-camera instances avoid global naming collisions. Different resolutions belong to their own producers, not to a monolithic surface layout.

C's useful addition is declaration identity and setup validation: create handles with a unique scope+version, bind each exactly once before seal, walk declared current-frame input handles to reject cycles, require a producer for every reachable current-frame handle, distinguish imported previous-frame handles and externally owned targets.
